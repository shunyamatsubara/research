Decision pipeline card

A language model reads. Rules decide. The ontology is the contract between them.

PartTurnsRepeats exactly?Typical failure
Read messy input → typed facts No. The same input can give different facts, even at temperature 0. Wrong value. Wrong class picked from the ontology. A value filled in that the input never said.
Ontology defines kinds of things, their fields, is-a links It is fixed, versioned data, not a process. A missing class. A wrong is-a link. Classes too broad to tell cases apart.
Decide typed facts → decision + trace Yes, for the same facts and the same rule version. A gap (no row matches) or an overlap (two rows match). An old rule version still running.

Questions to ask a vendor

  1. For one claim, show me which steps run as fixed code and which run through the language model.
  2. Are your rules run as code, or are they text that the model reads and applies?
  3. Run the same 200 claims five times. What share of the decisions are identical?
  4. How do you measure reading errors, and what happens when the model is unsure?
  5. Can you replay a past decision with that day’s rules and show which rule fired?
  6. Who owns the ontology, and how are changes reviewed and versioned?

This list grows in later lessons into the full vendor scorecard.

Rules of thumb

Deterministic given the facts, not given the input. A claim of “deterministic” almost always covers only the decide step.

Right shape is not right values. Structured outputs guarantee the fields and types, not that “red flag = no” is true.

Write a rule once, high in the tree. A rule about AdvancedImaging reaches every subclass through is-a, such as MRI_Knee.

The rules see only what the reader picked. If the reader picks a class that is too general, the right rule never runs, and nothing complains.

A good rule table is complete and has no overlaps. Every possible set of facts matches exactly one row. DMN calls this the “Unique” hit policy, and it can be checked by machine.

Even vendors say so. Palantir’s docs: deterministic functions “complement the non-deterministic reasoning of LLMs”. A “rule” that a model reads during reasoning is not a deterministic rule.

Unclear input stays unclear. If the note does not say it, no rule can know it. Route it to a person or ask for more information.
