試作：VLM の点から土台の 3D 座標へ（1〜4 章）

はじめに

「近づくまでは motion planning、掴むところはポリシー」という構成にすると、motion planning に渡す 3 次元の目標を、VLM の出力から作る必要がある。IK は分かっていても、その入力になる姿勢の作り方が抜けている。だから画素から 1 段ずつ、ロボットの土台の座標まで運ぶ計算が要る。

その答えは VLM の中ではなく、カメラの幾何にある。この記事は、RGB-D カメラ 1 台と VLM の 2D 出力という、よくある構成だけを扱う。座標変換は特に混乱しやすいので、前提から省かずに説明する。

1. VLM の点は、カメラから出る 1 本の光線になる

VLM が返すのは [y, x] = [750, 625] のような数で、そのままではメートル単位の目標にならない。しかも単位も順番もモデルごとに違う。Gemini は [y, x] を 0–1000、Molmo は x, y を 0–100、RoboPoint は x, y を 0–1 で返す。

だから最初に、元の画像の画素に戻す。画像は幅 640、高さ 480 なので、u = 625/1000 × 640 = 400、v = 750/1000 × 480 = 360 になる。順番を取り違えて [x, y] と読むと (480, 300) になる。これも有効な画素なので何も落ちず、本来の点から 125 mm ずれた場所を指す。

画素が決まっても、3D の点はまだ決まらない。その画素に写るものは、カメラの中心からその画素を通る 1 本の線の上のどこかにあるからだ。この線を「光線（ray）」と呼ぶ。つまり 1 画素は 1 本の光線であり、この光線がこの記事の道具になる。

図 1 の上の小さなパネルを見てほしい。640×480 の画像の中心が (320, 240) で、VLM の画素 (400, 360) はそこから右に 80、下に 120 の位置にある。次にパネル②の、上側の小さな三角形を見る。頂点にあるのがカメラの中心で、そこから 600 画素ぶん下にスクリーンがあり、スクリーンの上で中心から右に 80 画素の位置に、同じ点が打ってある。

この 600 が fx だ。「画像を、カメラの中心から 600 画素ぶん前に置いたスクリーンだと考える」と、fx の意味が分かる。スクリーンの大きさは画素で測り、世界はメートルで測る。単位が違うので、両方で共有できるのは比だけだ。その比が 80/600 = 2/15 ≈ 0.133 で、光線は前へ 1 m 進むと右へ 0.133 m 進む。縦も同じく、fy = 600 を使って (360 − 240)/600 = 0.2 になる。

スクリーンは考えやすくするための置き方で、実物のセンサーはレンズの後ろにあり、像も上下左右が逆になる。ただし傾きの比は同じなので、計算は変わらない。このモデルを「ピンホールカメラモデル」と呼び、fx, fy, cx, cy を「内部パラメータ（intrinsics）」と呼ぶ。cx, cy は画像の中心 (320, 240) のことだ。レンズの歪みは無視した。D435 級の color では歪みの係数がほぼ 0 と報告されている。

2. 深度が光線の上の 1 点を決める

光線だけでは、その上の 1 cm 先か 1 m 先かが決まらない。同じ画素に写る点は無数にあるので、このままでは掴む位置にならない。

図 1 のパネル②の大きい三角形を見てほしい。小さい三角形の光線をそのまま延ばした形で、薄い点が 2 つ打ってある。奥行き 0.30 m では右に 0.04 m、0.60 m では右に 0.08 m だ。3 点とも同じ画素 (400, 360) に写るので、画像を見ただけでは区別できない。

区別するのが深度（カメラから前方への距離）Z だ。この画素の深度の生の値は 750 で、1 単位が 0.001 m なので Z = 0.75 m になる。パネル②の一番下の点がそこで、2 つの三角形は相似だから 80 : 600 = X : 0.75 が成り立つ。X = 80 × 0.75 / 600 = 0.10 m であり、縦も 120 × 0.75 / 600 = 0.15 m だ。カメラから見た点は (0.10, 0.15, 0.75) m である。

ここに toy の偶然がある。0.75 を掛けると 2/15 の分母の 15 が消えるように、深度を選んである。だから X が丸い値になるだけで、実際のカメラでは割り切れない。同じ式から、この深度での 1 画素の幅は Z/fx = 0.75/600 = 1.25 mm と分かる。これは後で誤差を見るときに使う。

この計算を「逆投影（back-projection）」と呼ぶ。RealSense の SDK の deprojection 関数も、中身は同じ式だ。

ただし深度画像と color 画像は視点が違うので、同じ画素の深度をそのまま読めない。だから depth を color の視点に合わせ直す「align」を先に行う。深度が 0 の画素は測れなかった穴なので除き、マスクがあれば有効な画素の中央値を使う。中央値やマスクの縮小は一般的な工夫で、文献が定めた手順ではない。

3. 4x4 は「カメラの原点から軸に沿って歩く」計算だ

求めた (0.10, 0.15, 0.75) m は、カメラから見た数字だ。これを motion planning にそのまま渡すと、土台の原点から 10 cm、15 cm、75 cm の場所を目指す。物体はそこにないので、腕は別の場所へ動く。だから土台から見た数字に直す必要がある。

直すために、まず「座標系（frame）」を決めておく。座標系とは、原点が 1 つと、3 本の軸の向きのことだ。土台にも座標系があり、カメラにも座標系がある。点の数字は、原点からその軸に沿って何だけ進んだかを表すので、どの座標系で測るかで変わる。

toy では、同じ点がこう書ける。カメラの座標系では (0.10, 0.15, 0.75)、土台の座標系では (0.60, −0.15, 0.05) だ。点は動いていない。測る原点と軸が違うだけである。ここでも toy の偶然がある。カメラは土台の x 方向に 0.5 m、高さ 0.8 m の位置で、真下を向いている。だから軸の向きは符号が変わるだけで済む。

図 2 の左を見てほしい。カメラの x 軸は土台の +x、y 軸は土台の −y、z 軸は土台の −z（真下）を向いている。計算は「カメラの原点から出発し、カメラの 3 本の軸に沿って歩く」ことだ。x_c に 0.10、y_c に 0.15、z_c に 0.75 歩く。

土台の数字で書くと、次のようになる。

  • x = 0.5 + 1 × 0.10 = 0.60
  • y = 0 + (−1) × 0.15 = −0.15
  • z = 0.8 + (−1) × 0.75 = 0.05

z = 0.05 は、机の上 5 cm の物体の上面の高さと合っている。

図 2 の下の表が、この歩き方を 1 つにまとめた「4x4 同次変換」だ。1 列目 (1, 0, 0) はカメラの x 軸が土台の数字でどう見えるか、2 列目 (0, −1, 0) は y 軸、3 列目 (0, 0, −1) は z 軸を表す。4 列目 (0.5, 0, 0.8) は、カメラの原点が土台のどこにあるかだ。各列に 0.10、0.15、0.75 を掛けて足し、最後に 4 列目を足せば、上の 3 つの式になる。

では、なぜ一番下に (0 0 0 1) の行があり、点に 1 を足すのか。軸に沿って歩く部分は掛け算で、出発点を足す部分は足し算だ。点を (0.10, 0.15, 0.75, 1) と書くと、4 列目に 1 が掛かり、足し算も掛け算の中に入る。だから 1 回の掛け算で、回転と平行移動が同時に済む。下の行は、答えの最後の数が 1 のままになるように置いてある。

この表を T_base_cam と書く。読み方は「土台から見たカメラの姿勢」で、使い方は「カメラの数字を土台の数字に直す表」だ。カメラの座標系を土台から見たものなので「外部パラメータ（extrinsics）」とも呼ぶ。形は、FK で出す T_base_ee と同じだ。T_base_ee は手先の原点と軸を土台から見た表で、T_base_cam はその手先をカメラに替えたものである。

最後に落とし穴が 1 つある。この記事のカメラの軸は x が右、y が下、z が前方で、これを optical frame と呼ぶ。ROS のロボット本体の軸は x が前方、y が左、z が上で、camera_link はこちらに従う。2 つは回転が違うので、ROS の camera_link の姿勢をこの計算に使うなら、先に固定の回転で軸をそろえる。

4. T_base_cam はつなぎ合わせで作る

T_base_cam は、誰も直接は教えてくれない。カメラを手先に付けると、腕が動くたびにカメラも動くので、1 つの固定値では書けない。しかも掛ける順番や向きを 1 つでも間違えると、エラーは出ずに別の場所が返る。

そこで T を、下付き文字が打ち消し合うように掛ける。T_a_b · T_b_c = T_a_c のように、内側の b が消えて外側の a と c が残る。

図 3 の上の鎖が、固定カメラ（eye-to-hand）だ。base から cam への T_base_cam が 1 つあるだけで、カメラは動かないので、一度測れば一定である。下の鎖が手先カメラ（eye-in-hand）だ。base から ee へは、撮影した瞬間の関節角 q から FK で T_base_ee(q) を出す。ee から cam へは T_ee_cam を掛ける。つまり T_base_cam = T_base_ee(q) · T_ee_cam で、ee が打ち消される。q は撮影の瞬間の値でなければならない。腕が動いた後の値を使うと、その分だけ点がずれる。

一定の部分は、測って求める。ロボットにチェッカーボードを何通りもの姿勢で見せ、そのときの手先の姿勢とカメラから見た板の姿勢を集める。そこから未知の T を解く方法を「ハンドアイキャリブレーション」と呼び、式は AX = XB の形になる。固定カメラでは T_base_cam が、手先カメラでは T_ee_cam が求まる。

測定ツールが、欲しいのと逆向きの T を返すことがある。OpenCV の calibrateHandEye は、手先カメラでは gripper から見た camera を返す。これは T_ee_cam と同じ向きだ。しかし入力の取り方で結果の向きが変わるので、返ってきた T の下付き文字を必ず確かめる。逆向きなら、逆の変換を取る。

逆の変換は、数字の符号を変えるだけでは作れない。回転の部分は転置し、原点の部分は −Rᵀt にする。toy の T_base_cam では、R = diag(1, −1, −1) なので Rᵀも同じ形だ。Rᵀ(0.5, 0, 0.8) = (0.5, 0, −0.8) で、符号を変えて T_cam_base の原点は (−0.5, 0, 0.8) になる。確かめるために、土台の点 (0.60, −0.15, 0.05) に掛ける。x = 0.60 − 0.5 = 0.10、y = −1 × (−0.15) = 0.15、z = −1 × 0.05 + 0.8 = 0.75 で、カメラの数字に戻る。もし原点の符号だけを変えて (−0.5, 0, −0.8) としていたら、カメラの原点 (0.5, 0, 0.8) は (0, 0, −1.6) に行き、原点に戻らない。

キャリブレーションは時間とともにずれると報告されている。OK-Robot は、RealSense が時間とともに miscalibrate して、操作の失敗につながると述べている。測った T_base_cam や T_ee_cam を、いつまでも正しいとは考えない。
