T_base_cam は、誰も直接は教えてくれない。カメラを手先に付けると、腕が動くたびにカメラも動くので、1 つの固定値では書けない。しかも掛ける順番や向きを 1 つでも間違えると、エラーは出ずに別の場所が返る。

そこで T を、下付き文字が打ち消し合うように掛ける。T_a_b · T_b_c = T_a_c のように、内側の b が消えて外側の a と c が残る。

![Figure 3](#fig-3) — 2 本の鎖の図。固定カメラは base →T_base_cam→ cam → point。手先カメラは base →T_base_ee(q)（撮影時の FK）→ ee →T_ee_cam（ハンドアイキャリブレーション）→ cam → point。規則 T_a_b · T_b_c = T_a_c を添える。

図 3 の上の鎖が、固定カメラ（eye-to-hand）だ。base から cam への T_base_cam が 1 つあるだけで、カメラは動かないので、一度測れば一定である。下の鎖が手先カメラ（eye-in-hand）だ。base から ee へは、撮影した瞬間の関節角 q から FK で T_base_ee(q) を出す。ee から cam へは T_ee_cam を掛ける。つまり T_base_cam = T_base_ee(q) · T_ee_cam で、ee が打ち消される。q は撮影の瞬間の値でなければならない。腕が動いた後の値を使うと、その分だけ点がずれる。

一定の部分は、測って求める。ロボットにチェッカーボードを何通りもの姿勢で見せ、そのときの手先の姿勢とカメラから見た板の姿勢を集める。そこから未知の T を解く方法を「ハンドアイキャリブレーション」と呼び、式は AX = XB の形になる。固定カメラでは T_base_cam が、手先カメラでは T_ee_cam が求まる。

測定ツールが、欲しいのと逆向きの T を返すことがある。OpenCV の calibrateHandEye は、手先カメラでは gripper から見た camera を返す。これは T_ee_cam と同じ向きだ。しかし入力の取り方で結果の向きが変わるので、返ってきた T の下付き文字を必ず確かめる。逆向きなら、逆の変換を取る。

逆の変換は、数字の符号を変えるだけでは作れない。回転の部分は転置し、原点の部分は −Rᵀt にする。toy の T_base_cam では、R = diag(1, −1, −1) なので Rᵀも同じ形だ。Rᵀ(0.5, 0, 0.8) = (0.5, 0, −0.8) で、符号を変えて T_cam_base の原点は (−0.5, 0, 0.8) になる。確かめるために、土台の点 (0.60, −0.15, 0.05) に掛ける。x = 0.60 − 0.5 = 0.10、y = −1 × (−0.15) = 0.15、z = −1 × 0.05 + 0.8 = 0.75 で、カメラの数字に戻る。もし原点の符号だけを変えて (−0.5, 0, −0.8) としていたら、カメラの原点 (0.5, 0, 0.8) は (0, 0, −1.6) に行き、原点に戻らない。

キャリブレーションは時間とともにずれると報告されている。OK-Robot は、RealSense が時間とともに miscalibrate して、操作の失敗につながると述べている。測った T_base_cam や T_ee_cam を、いつまでも正しいとは考えない。
