前章で得た (0.60, −0.15, 0.05) m は、向きを持たない点だ。motion planning が要るのは姿勢で、位置に加えて「グリッパーがどちらを向くか」と「手首をどれだけ回すか」まで決まっていなければならない。しかもこの点は物体の見えている上面にある。目標に置きたいのは指先の「TCP」（2 本の指の間の点）だが、多くの planner はアームの先端の「フランジ」（グリッパーをねじ止めする面）を目標として受け取る。この例では両者は 0.15 m 離れているので、フランジをこの点に送ると、指先は物体に 0.15 m めり込む位置を目指してしまう。

1 本の光線は、物体がどう置かれているかを何も教えてくれない。しかしマスクの全画素に 3 章と同じ計算をすれば、画素ごとに 1 つずつ 3D の点が得られる。この点の集まりを「点群（point cloud）」と呼ぶ。点群は物体の見えている形なので、向きの手がかりになる。

向きの決め方は、よく使われるものが 2 つある。1 つ目は真上から掴む方法だ。接近方向をまっすぐ下にして、グリッパーの z 軸を土台の −z に合わせる。手首の回転（yaw）は、点群を真上から見て、いちばん長く伸びる向き（主方向）から決める。Gemini Robotics-ER の報告も、真上からの把持までだ（C5）。

この例の箱は上面が 8 cm × 4 cm で、長辺が土台の x 方向に伸びている。主方向は x なので yaw = 0° で、指は 4 cm の辺をはさむ向きに閉じる。

2 つ目は把持ネットワーク（AnyGrasp、Contact-GraspNet）だ。点群を入力すると、6-DoF（位置 3 つと向き 3 つ）の把持の候補を多数出す。OK-Robot と CoPa は、候補のうち VLM のマスクに入るものだけを残し、最高の点数を選ぶ（A24、C15）。MOKA は、VLM の点にいちばん近い候補を選ぶ（A20）。つまり VLM は「どこを」を決め、幾何か把持ネットワークが「どう掴むか」を決める。ただし出力の座標系とグリッパーの軸の約束は、読んだ README には書かれていない。使う前に必ず確かめる（A14、A15）。

向きが決まれば、把持姿勢は 4x4 の表で書ける。4 章と同じく、1〜3 列がグリッパーの x, y, z 軸を土台の数字で表し、4 列目が位置だ。この例では x_g = 土台の +x、z_g = 土台の −z で、残りの y_g は、x と z が決まると右手系の約束（x, y, z の順に右手の親指・人差し指・中指の向き）で 1 つに決まり、土台の −y になる。

    T_base_grasp = [[1, 0, 0, 0.60], [0, −1, 0, −0.15], [0, 0, −1, 0.05], [0, 0, 0, 1]]

簡単のため TCP を上面に置いたが、実際の把持はもう少し低い。

次に、物体の手前に止まる「pre-grasp」姿勢を作る。接近方向に沿って 0.10 m 戻る。T_base_pre = T_base_grasp · Trans(0, 0, −0.10) と書き、Trans はグリッパーの座標系で測った平行移動を表す。z_g が土台の −z を向くので、−0.10 は土台の z では +0.10 になり、位置は (0.60, −0.15, 0.05 + 0.10) = (0.60, −0.15, 0.15) m だ。向きは変わらない。5 章の規則では、右から掛けた Trans の数字はグリッパーの座標系のものになる。だから「grasp · オフセット」は「グリッパー自身の軸に沿って動く」を意味する。左から掛ければ土台の軸に沿った移動になり、z は 0.05 − 0.10 = −0.05 m と机の下に潜る。戻す距離は 5〜10 cm が慣習で、出典はない。

planner の目標がフランジのときは、TCP の姿勢に T_flange_tcp の逆行列を右から掛ける。T_flange_tcp はフランジから見た TCP で、ここでは z 方向に 0.15 m だ。フランジは TCP より 0.15 m 上にあるので、把持では z = 0.05 + 0.15 = 0.20 m、pre-grasp では z = 0.15 + 0.15 = 0.30 m になる。x と y は (0.60, −0.15) のままだ。

想定している構成では、motion planning がアームを pre-grasp の姿勢まで運び、そこから学習したポリシー（VLA）が最後の 10 cm を引き継ぐ。ポリシーがどれだけの位置ずれを吸収できるかは、探した範囲のどの出典にも数値がなかった（C41）。ここは未解決のままだ。
