Method notes (short):
- Protocol lists were fetched as the vendors' own PDFs/pages, converted to text, and searched for terms (b-CAP, Denso, ROS, DDS, RTPS, VDA, WebSocket, MQTT, OPC, Profinet, PROFIsafe, FSoE, CIP Safety). "Absent" below always means "not in the text of that document", not "not supported".
- Notes carry the exact quote behind each key claim. Tags: [factory], [product], [supply-chain], [general].
- Interpretation is kept in notes and marked "Interpretation:".
- The WebSearch budget of the session ran out partway (shared limit), so some targets were found by fetching known vendor URLs or by GitHub code search (GitHub's own API) for URLs, not by web search. See the last section.

## What I could not find

- Siemens, Pilz and Bosch Rexroth ctrlX SAFETY manuals (monitored quantities, parameter CRC, acceptance test). Siemens Industry Online Support and Pilz returned HTTP 403 to automated fetches; the Rexroth documentation portal (docs.automation.boschrexroth.com) and the ctrlX SAFETY product page returned a JavaScript shell with no text; GitHub code search found no mirrored URLs. Rockwell GuardLogix (G35, G36) was used as the one safety-PLC manual that could be read. No PROFIsafe F-parameter CRC (F_Par_CRC) source was reachable either (PI pages returned no text on it).
- Denso Safety Motion manual (monitored quantities, parameter protection): behind the Denso Robot member login; only the public RC8A page was read (G34).
- IEC 61496-3 clause text on immunity to other light sources, ambient light and reflective targets: the IEC webstore preview returned an HTML page, not the PDF. Only SICK's own citation of the standard (G31) and SICK's statement of the "3 klx in the scan plane" footnote were read; I did not read what the standard itself requires or how the test is run.
- nanoScan3 behavior under a deliberate optical attack (spoofed pulses, injected light): the manual only treats interference as an installation and availability matter (G31); no SICK statement on intentional optical manipulation or on how the scanner detects it was found.
- A current Claroty per-protocol list (MQTT, OPC UA, EtherNet/IP): the public documents found are the 2018 list (G20) and the 2023 data sheet (G17); the current list is in customer-only material or not public. Claroty's protocol-level coverage of config-change detection is therefore unverified.
- Cisco Cyber Vision feature documents (event types for program/firmware/config change, baseline behavior): the product page and data sheet URLs tried returned HTTP 403; only the protocol list (G4) was read.
- Any OT-IDS vendor feature that treats an ML model host, model file or weights as an asset class: none found in Nozomi (alerts reference, configuration reference, June 2026 physical-AI blog), Dragos (protocol sheet, two blog posts), Microsoft (inventory page) or Claroty (data sheet). This is absence in the documents read, not proof that no such feature exists.
- Whether any OT IDS decodes VDA 5050 message content, b-CAP commands, ROS 2 / DDS (RTPS) traffic, or whether a model or recipe file transfer to a non-PLC host raises an alert: no vendor document states it either way (G6, G15). It needs a vendor answer or a lab test.
- Firewall or conduit-enforcement products (zone/conduit rules on OPC UA, MQTT): no vendor document on application-layer filtering of those protocols was read; the "zones" in G18 and G19 are monitoring constructs. IEC 62443-3-3 text (SR 5.2 zone boundary protection) is paywalled and was not read.
- A 2025-26 OT-IDS vendor white paper specifically on securing ML models in OT, to compare with the CISA joint guidance (C42-C47): the closest items are the Nozomi blog (G21) and the Dragos blog (G22); the Claroty post "Understanding AI-Powered Cybersecurity in OT Environments" (https://claroty.com/blog/understanding-ai-powered-cybersecurity-in-ot-environments) is listed on Claroty's blog index but was not opened (its title suggests AI used for defence). No TXOne or Armis document was checked.
- Web search was unavailable after the shared search budget ran out, so coverage of Nozomi, Claroty and Dragos pages relies on fetching their documentation sites directly; pages that sit behind login (Claroty docs, Nozomi support portal) were not tried.
